### 3.2 ★ 一条任务书事实被 IL 证伪（**并连带更正了长期记忆**）

任务书 §2.2 与 §0.4.2 说：「去重键是相对文件夹根的路径，**所以** `<mod>\1.6\Defs\A.xml` 与 `<mod>\Defs\A.xml` 是两个不同的键、**会同时被加载**」。

**这是错的，且与它自身的前提矛盾。** 主理人自己写 IL 解码器反汇编 `Verse.DirectXmlLoader.XmlAssetsInModFolder`（527 字节）：

```
IL_0024 ldc.i4.0 → 按 list 顺序（降序=高优先级在前）遍历
IL_0091 get_FullName
IL_0096 ldloc.s 6 (= list[i])  → IL_0098 get_Length / IL_009D +1
IL_009F String::Substring      → key = FullName.Substring(list[i].Length + 1)
IL_00AB Dictionary::TryAdd     → 先到先得
```

两者相对**各自文件夹根**的路径**都是 `Defs\A.xml`** ⇒ **同一个键、只留一份**（`list[0]` 赢）。

**推论（本轮最值钱的一条）**：真正会同时进候选的是**相对键不同**的同名 def —— 那才是 `RD2026` 的来源；把「绝对路径不同」当成「都加载」会造出成批的**假 RD2026**。

> ⚠️ 这条错误此前已进入**长期记忆**（《引擎加载文件夹的权威语义》第 ④ 条），并从中复制进了 Task 3 任务书。关键记忆轨已由执行者建议更正并注入；**长期记忆轨的更正建议已另发**。

**① `api list` 不需要类型名 —— 帮助文案在骗人**

### ★ 门禁修复：`build-all.ps1` 的「构建 0 警告 0 错误」原来是写死的字符串

**这是本轮复验里比 9c 本身更值钱的发现。** 我修 `api list` 时引入了一条 `CS8604`，构建输出里明明有 4 行 `warning CS####`，而 `build-all.ps1` 的汇总行照样打印「构建 0 警告 0 错误」——因为：

```powershell
dotnet build ... -v:q --nologo @msbuildArgs
if ($LASTEXITCODE -ne 0) { Write-Error "build failed: $p"; exit 1 }   # 只看退出码
...
Write-Host ("[{0}] 构建 0 警告 0 错误 | ...")                          # ← 字面量，从未被计算
```

**统计数据描述的是宣称，不是实际动作** —— 与本项目反复追的 `filesParsed = changed.Count`（判定输入 vs 实际动作）、`$h.Count` 被同名键遮蔽、`Select-Object -First` 改写 `$LASTEXITCODE` 是同一族。**必须记住：本项目过去所有「0 警告 0 错误」的说法，都是靠人肉读 raw 日志得来的，不是这条门禁判的。**

修法：收集每个工程的构建输出 → `Where-Object { "$_" -match 'warning\s+[A-Z]+\d+' }` → **有一条就 `exit 1`** → 汇总行打印实测值 `$totalWarnings`。两个实现细节（都必须留下）：
- **必须按行去重**（`Select-Object -Unique`）：MSBuild 把同一条警告打印两遍（正文一次 + 末尾汇总列表一次），且 `RimDev.Cli` 会作为 `SelfTest` 的依赖再被构建一次 ⇒ 不去重会把「2 条警告」报成「8 条」（实测 8 → 去重 4 = 2 个代码 × 2 个 TFM）。
- 不要把构建输出接给会提前终止管道的 cmdlet（会改写 `$LASTEXITCODE`）；先收集再判。

**门禁必须验证它自己会响**（否则只是把一句死文案换成一段死代码）：注入一条 `int probeUnusedWarning = 0;`（CS0219）⇒ `build-all` **exit 1**，报 `build produced 4 warning line(s) …: RimDev.Cli\RimDev.Cli.csproj`；撤销后 `exit 0`、日志 0 条 warning。附带好处：并发跑导致的 `MSB3026`（DLL 被占用）现在会当场判红，不再「6 条警告 + 汇总写 0 警告」地混过去。

**我自己在同一轮里踩的坑（同一族，记下来）**：第一次看构建日志时我用了 `Select-String '…|CS\d|…' | Select-Object -Last 8` —— **`-Last 8` 把 `ApiCommand.cs:88` 的第二条 CS8604 截掉了**，于是我「修完 CS8604」就继续往下走，直到门禁修好后注入探针才把它暴露出来。判据：**对 grep 结果做 cap 之后得到的「零命中/已修完」结论一律不算数**，要重跑不带 cap 的版本（这与「`Select-Object -First N` 改写 `$LASTEXITCODE`」是同一族的第二个面孔）。

### 5.6 ★★ 新发现的假阳类：`FieldNameCheck` 用「def 起始行」当归属键（**已由 Task 5c 修掉**，修法见 §4e）

**触发条件**：一个 XML 文件里**多个 def 的起始行相同**（紧凑单行排版很常见）。这不是错写法 —— RimWorld 完全接受。

**机制**（`RimDev.Core/Checks/FieldNameCheck.cs`）：

```csharp
// 采集侧：defLine = 该 depth==1 元素的起始行；depth==2 的元素全部记到当前 defLine 名下
if (reader.Depth == 1) { defLine = line; continue; }
if (reader.Depth == 2 && defLine >= 0) list.Add((defLine, reader.Name, line, ...));
// 消费侧：按【行号】取桶 —— 同一行的多个 def 因此共享同一个桶
if (!elementsByDefLine.TryGetValue(d.Line, out var elements)) continue;
```

⇒ 同一行的 N 个 def 各自拿到**N 个 def 的全部一级子元素的并集**，于是「另一个 def 的字段」被拿本 def 的类型去校验。

## 8. 方法论教训（本期累积，可直接复用）

1. **人工转写反编译文本只能当假设**：Task 1 转写被实测推翻 9 条；Task 3 任务书里的去重键结论同样是转写错误，靠 IL 证伪。
2. **每条转写都要配一条「能证伪它」的用例**，而不只是「能验证它」的。Task 2c 的两条证伪用例当场推翻了任务书。
3. **对着活跃写入中的语料做精确等值断言 = 假失败制造机**：正解是**把锚点落在不可变子集上**（`1668−42 = 1626`），而不是放宽成「基线 ± 容差」。
4. **零假阳门要分两层**：官方语料（证明不误报合法写法）＋ **会触发该规则形态的第三方语料**。只有前者时，规则能在生态上制造几万条噪音而门禁全绿。
5. **诊断的假阳比漏报更贵**：判据是「使用者会不会直接把报告关掉」。
6. **报数字前先问「这是我量的，还是我量的方式的产物」**：`[Unsaved]` 字段数存在**声明口径 427** 与**可见性口径 3,962** 两种，都对但不可混用。
7. **验收要显式贴出被断言项的计数**：主理人上轮只读了构建输出尾部，漏掉 1 条警告，导致「0 警告」的错误结论被记录了一轮。
    · ★ **Task 9c 复验时再次复发**：这次用 `Select-String ... | Select-Object -Last 8` 截断，漏看了第二条 `CS8604`，于是「CS8604 已修完」被当成事实（后来靠新门禁抓出来）。⇒ **对 grep 结果做 cap 之后的任何「零命中 / 已修完」结论一律不算数**，要重跑不带 cap 的版本。
8. **`[IO.File]` 用进程 CWD，不认 PowerShell 的 `cd`** —— 相对路径会静默读到别处。
9. **`edit` 的 3 字符锚点是位置相关的**：同一批 `edits` 里靠前的条目会移动靠后条目的锚点（`E_STALE_RANGE`）；**按行号从下往上改**，或拆成多次调用。
10. **门禁里写「其余都不许变」时，必须逐个字段独立推导它覆盖的每一项**（Task 4b 实证）：主理人在门禁 4 里列了 13 个码要求「不变」，却只独立推导过自己算过的 RD2004/RD2026 —— 其余项是**假设**。结果 RD2025 因同一个修复合法地 −90，一份**正确的**实现被判成 `FAIL`。
    · 判据：门禁里每一个数字，都要能回答「我是**算**出来的，还是**抄**上一轮的」。抄来的就是假设，必须标注为假设或补推导。
11. ★★ **「语料触发的失败」≠「语料的缺陷」**（Task 5b 复核实证）：同一份观测（RD4001 报 `ThingDef TF_ThreatForge 上没有字段 jobString`）在两次记录里给出了两个不同的解释 —— 先记成「写入者把字段写在 `<ThingDef>` 下」，真因是**工具把「def 起始行」当归属键、同一行的多个 def 互相串了子元素**。判据：**遇到「某 mod 的这一条怎么突然坏了」时，先打开 DOM 看祖先链**（一条命令），不要从「某关键字 0 命中」反推结构 —— 后者只能证伪「有包裹」，推不出「字段挂在哪」。
    · 同源纪律：**任何「A 触发、B 才是原因」的失败，都要能回答「换成一份等价但排版不同的输入，还在不在」**。
12. **同一个「身份键」坑会复发，修一处不够**：Task 5a 修过 `ParentChainCheck` 的 `(FileAbs, Line)`（改成对象引用），Task 5b 复核时又在 `FieldNameCheck` 撞到同一类问题（行号当归属键）。⇒ 修这类缺陷时要**全仓扫「把行号当身份/归属键」的地方**，而不是只修被当场抓到的那一处。
    · ★★ **Task 5c 的修法值得单列**：把「两侧对『什么算一个 def』的判据必须一致」做成**运行期 parity 门禁**（个数 + 逐个行号），不一致就报 RD2001 并**跳过该文件**。理由：这类键改错之后的典型症状不是崩溃，而是**整段偏移**（每个 def 读到邻居的桶）—— 与原来的「张冠李戴」一样静默。**能静默错的地方，就要让它响亮地失败。**
    · 配套判据：改完必须验证**门禁本身不误报**（本轮 `RD2001` 从 14 → 14 未变，才是「门禁没有把好东西打掉」的证据）。
13. ★★ **验收门禁的汇总行必须是「算出来的」，不能是「写出来的」**（Task 9c 复核实证）：`build-all.ps1` 汇总行那句「构建 0 警告 0 错误」是**字面量**，MSBuild 的警告从未被计数 —— 我故意注入一条 `CS0219` 时它照样打印「0 警告」。这与第 7 条是同一件事的两个层次：第 7 条是「**人**读数时截断了」，本条是「**工具自己就没在算**」。
    · 判据：凡汇总行（0 警告 / 0 失败 / 0 未解析 / 0 假阳），都要能回答「这个数字是谁算的」；并且**必须用一次故意的失败证明它会变红**（本轮：注入 CS0219 ⇒ `exit 1` 并点名工程；撤销 ⇒ `exit 0` 且日志 0 条 warning）。
    · 修计数口径时注意 MSBuild **每条警告打印两遍**（正文一次 + 末尾汇总一次），且被依赖的工程会再构建一次 ⇒ 不去重会把「2 条」报成「8 条」。**计数器的口径要写进报错文案**（「每个 TFM 各计一次」），否则下一个人会以为多了 6 条。
    · 追溯影响：本项目此前所有「0 警告 0 错误」的结论，来源都是**人肉读 raw 日志**，而不是这条门禁；现在它是真的在判。
14. ★ **主理人给的「硬前提表」也只是假设，执行者的独立复现必须可能推翻它**：Task 5b 任务书写了 8 条引擎口径，执行者在自测进程内复现后**扩到 12 条**（多的 4 条恰好是「引擎看起来像 bug」的那些）。任务书已明确「主理人的 pwsh 运行只能当假设」，这条纪律有效；**下任务书时对每条口径都要写清「这是谁在什么条件下测的」**。
