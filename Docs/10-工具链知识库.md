## 一、外部工具生态对照

调查时间 2026-11-09/10。目的：搞清楚「RimDev 该做什么、不必做什么」。

### 1.1 全景表

| 工具 | 定位 | 与 RimDev 的关系 |
|---|---|---|
| **[RimSearcher](https://github.com/kearril/RimSearcher)** V3 | 游戏内 mod 导出 `defs.db`(SQLite) + CLI 查询 + 反编译服务 | **运行时真值源**。架构与我们相反：他跑在游戏里拿真值，我们跑在游戏外重建 |
| **[rimpatch](https://pypi.org/project/rimpatch/)** | 补丁 XPath 检查器（Python） | **补丁层最强参照**。报告形态值得学，见 §1.3 |
| **[RimSort](https://rimsort.github.io/RimSort/user-guide/sorting-algorithms)** | 加载顺序排序器（拓扑排序 + 社区规则库） | **排序领域权威**，与静态分析无关，不重叠 |
| **[RimCrow](https://github.com/Inky-Feather/RimCrow)** | 桌面模组管理器（扫描/排序/备份/下载/日志/AI） | **模组管理层**，**不分析 Def**（177 py / 101k 行，全库仅 `parser_dlc.py` 提到 defName）⇒ 互补 |
| **[rimworld-modder-mcp](https://socket.dev/nuget/package/cryptiklemur.rimworld-modder-mcp)** | .NET 10 的 MCP 服务，做 XML defs/继承/补丁/兼容检查 | 同类实现，可对照参考 |

### 1.2 RimSearcher 的架构启示（重要）

它的自述把我们一直以来的困境说得很准 —— 记下来当设计原则：

> **Static Data Illusions**: RimWorld loads, inherits, and deeply merges tens of thousands of XML definitions via PatchOperations at runtime. Reading raw static XML files on disk frequently misleads models with inactive overrides, unapplied inheritance, and dynamic runtime injections.

⇒ **「读静态 XML 会骗人」是这个领域的核心难点**，三个具体来源：
1. **inactive overrides**（未启用 mod 的覆盖）
2. **unapplied inheritance**（继承没应用）
3. **dynamic runtime injections**（运行期注入）

RimDev 的应对：1 靠「启用集判定」，2 靠 `InheritanceLayer` 离线重建，3 靠 `DefGenerator` 建模（Task 6b）+ 承认边界（诚实写进报告）。

**它做不到的事（对我们有用）**：
- `defs` 表对 `(def_name, def_type)` 是 **UNIQUE 索引** ⇒ **只留赢家**，查不到「原本有几份、谁覆盖了谁」
  - 实测：`MapGen_AncientComplexRoomLoot_Default` 离线看到 4 份（Core/Ideology/FrozenSnowFox×2），运行时库里只剩 Ideology 那份
  - ⇒ **覆盖审计是我们的活，不是它的**
- `get` **不返回来源 mod**（253 个 key 里无 `mod_name`/`source_file`），`find`/`list` 才返回
- `find` 是**字面后缀精确匹配**：`find costList.thingDef Steel` → `[]`（真实路径是 `costList[0].thingDef`）

### 1.3 rimpatch 的报告形态（最值得学的 UX）

它把「补丁打空了」写成这样：

```
Patches/BonelessAlphaAnimals.xml:23
  PatchOperationAdd matched 0 nodes
  xpath: /Defs/ThingDef[@Name="AA_PseudoBaseMechanoid"]/statBases
  deepest match: Defs (1 node) - no ThingDef with @Name="AA_PseudoBaseMechanoid" among active mods
  in: PatchOperationFindMod > PatchOperationSequence > PatchOperationAdd
  skipped as a result: PatchOperationAdd (line 30), ... and 71 more
  mod: sihv.rombones
```

**六段结构**：文件:行号 / 意图 / 目标(xpath) / **最深匹配点** / 上下文链 / **连带影响 + 归属**

RimDev 的 `RD2009` 现状（`PatchLayer.cs:433`）：只有「匹配 0 个节点」+ `evidence{outcome, operationClass, xpath, matched}`。
**缺**：最深匹配点、连带影响、上下文链。

## 二、本轮体检：四条真缺陷

体检方法：三个只读代理（补丁层 / 运行时对账 / 诊断归因）+ 主理人独立复算 + RimCrow 源码盘点。

### ★ 先说结论：三个初始假设，两个被推翻

| 原以为 | 实测 | 证据 |
|---|---|---|
| `PatchOperationSequence` 首败中止**没建模** | **已建模** | `PatchLayer.cs:634-646`：`if (!ApplyElement(...)) { worker = false; break; }`；自测 `Phase3Task4Cases.cs:260-292` 已钉住 |
| 主要缺口是「补丁层能力不足」 | 真缺陷是 **`return false` 让跳过被当成失败** | `PatchLayer.cs:421` → `:643` |
| 3,971 条悬空是「离线 vs 运行时偏差」 | **82% 是引用方 mod 未启用**，与对账无关 | 见 §2.2 |

**方法论教训**：**读代码之前先 grep 关键词**（`Sequence` 命中 `PatchLayer.cs:634` 只要一次搜索），比读任务书推断快得多。
我最初因为「rimpatch 有这个能力」就假定我们没有，是**从对方的功能反推自己的缺口**，方向错了。

### 2.1 缺陷 ①：`--scope all` 把未启用 mod 的引用也算进去

| 项 | 内容 |
|---|---|
| 位置 | `engine/RimDev.Core/Checks/ReferenceCheck.cs:725`（**唯一** RD3001 发射点） |
| 量级 | **3,256 条**（占 3971 的 82%） |
| 性质 | 纯假阳。`--scope all` 扫 4,034 个 mod，只有 630 个启用；未启用 mod 的悬空引用不影响当前游戏 |
| 修法方向 | 引用方 `ModPackageId` 不在启用集 ⇒ 降级 `Severity.Info` + `Evidence["reporterEnabled"]="false"`。**不要直接不报**（会丢「这个 mod 装坏了」的信息） |

**权威分类（已闭合，`无 mod` = 0 说明归因完整）**：

| 类别 | 条数 | 占比 |
|---|---|---|
| 官方内容 | 1 | 0.03% |
| **引用方未启用** | **3,256** | 82.0% |
| 引用方已启用（保 error） | 714 | 18.0% |
| 合计 | 3,971 | ✓ |

#### ★★ 口径陷阱：必须大小写不敏感（43 vs 714）

- `ModsConfig` 的 activeMods **全部小写**（630 条，0 条大小写不符）
- 但 `RawDef.ModPackageId` **保留原始大小写**（如 `VanillaExpanded.VanillaAnimalsExpanded`）
- 大小写**敏感**匹配 → 已启用 **43** / 未启用 3,927（**错误的初稿数字**）
- 大小写**不敏感**匹配 → 已启用 **714** / 未启用 3,256（**正确口径**）

理由：
1. 引擎语义就是 lower 建键（`ModLister.GetActiveModWithIdentifier`，IL 实证见 `InheritanceLayer.cs:540-554`）
2. `ActivePackageIds` 由 `NormalizeActiveModIds` 产出，**全是小写**
3. 按 43 写断言会把 **671 条真缺陷降成 info = 假阴，比假阳更贵**

**连带坑**：官方 packageId 是 `Ludeon.RimWorld.Anomaly` 这种大小写，**必须 lower 后查**，否则唯一的真阳性 `Ambient_MetalHell` 会被误降级。

> 这条是本轮**执行者拒绝迁就任务书**救回来的。任务书原写 43，执行者实测出 714 并坚持不按 43 写断言 —— 这是正确行为，记在此处作为范例。

### 2.2 缺陷 ②：全限定子类名未归并

| 项 | 内容 |
|---|---|
| 位置 | `engine/RimDev.Core/Defs/DefScanner.cs:173` —— `DefType: reader.Name` |
| 量级 | ~269 条 + 影响 RD2017/RD2004/RD2025 |
| 性质 | 真缺陷。元素名是 `AlienRace.ThingDef_AlienRace` 时，它**不算 ThingDef** |

**最小复现（逐字节核对）**：

```xml
<!-- workshop\294100\3560667190\1.7\Defs\AlienRace\AlienRaceSettings.xml:2-4 -->
<AlienRace.ThingDef_AlienRace Name="BANW_KivotosStudent" ParentName="BANW_StudentThingBase">
    <defName>BANW_KivotosStudent</defName>
```

结果：`<race>BANW_KivotosStudent</race>`（`PawnKindDef.race` 期望 ThingDef）被判悬空，**同一目标报 151 次**。

**全库规模（rg 实测，官方+本地+工坊）**：

| 元素名 | 出现次数 |
|---|---|
| `AlienRace.AlienBackstoryDef` | 12,554 |
| `ApparelPaperPattern.ApparelPaperPatternDef` | 5,350 |
| `TorannMagic.TMAbilityDef` | 2,856 |
| `AlienRace.BackstoryDef` | 2,084 |
| `VEF.Abilities.AbilityDef` | 1,904 |
| `WHands.ClutterHandsTDef` | 1,202 |
| `Vehicles.VehicleTurretDef` | 1,099 |
| `VFECore.Abilities.AbilityDef` | 968 |
| `AlienRace.ThingDef_AlienRace` | 907 |
| `VFEProps.PropDef` | 869 |

共 20+ 种。

#### ⚠️ 已知陷阱（项目已踩过，不能再踩）

**元素名含 `.` 时禁止退化到简单名。** `VEF.Abilities.AbilityDef` 取末段 `AbilityDef` 会兜底命中 `RimWorld.AbilityDef`，实测造出 **17,623 条假阳**（记在 `ManagedAssemblyCatalog.cs:36-40`）。

- `ManagedAssemblyCatalog.Find()` 的简单名退化是给 **api/name 交互查询**用的**有意设计**（注释 `:171-179` 明说）
- XML 元素名/Class= 必须用 `ResolveXmlTypeName`（`:213`），它**含点只认全名精确、绝不退化**

#### ★ 技术路线：用元数据读继承链（已实测可行）

**现状**：`ResolveXmlTypeName` 只查官方程序集（`ManagedAssemblyCatalog.Load(env.ManagedDir)`），mod 的 `Assemblies/*.dll` **没被加载**。
⇒ `AlienRace.ThingDef_AlienRace` 直接返回 null（`api probe` 实测 RD4004 TypeNotFound）。

**验证过的解法**：`System.Reflection.Metadata` + `PEReader` 只读元数据，**不加载程序集**（零 `BadImageFormatException` 风险）。

探针实现在 `_tmp/mdtype/`（44 行，`net10.0`，零外部依赖），已编译通过。
原理：`MetadataReader.TypeDefinitions` → `GetTypeDefinition(h).BaseType` → 沿链走，遇 `TypeReference` 说明基类在外部程序集。

**为什么这条比 `Assembly.LoadFrom` 好**：mod DLL 是 net472（1.6 时代编译），RimDev 跑 net10，加载有崩的风险（`Docs/08` 记过 net8 载 1.7 Assembly-CSharp 会 `ReflectionTypeLoadException`）。**元数据读取不执行任何代码**。

**另一条辅助判据：使用侧反推**
`<PawnKindDef><race>X</race>` 且 `PawnKindDef.race` 字段类型是 `ThingDef` ⇒ X 必然是 ThingDef（或子类）。
但**必须配独立佐证**（X 确实有 `<defName>` 定义），否则引用方写错会把不存在的名字也"反推"成合法类型。

### 2.3 缺陷 ③：跳过被当成失败（补丁层三态缺失）

| 项 | 内容 |
|---|---|
| 位置 | `engine/RimDev.Core/Defs/PatchLayer.cs:421`（自定义 Class 跳过）→ `:643`（Sequence 遇 false 就 break） |
| 性质 | **实现分歧**。引擎里那个自定义补丁类是**真执行**的；我们"不执行它"被父 Sequence 解释成"它失败了"，于是**中止后续所有兄弟操作** |
| 后果 | 一旦语料里有 `Sequence` 包着自定义类，就会在 Sequence 后半段刷出**成片假阳 RD2009** |
| 现状 | 本机 active 集 `customClassSkipped=0`（`_tmp/t10-active.json`），所以尚未暴露 |
| 修法方向 | 把「跳过」改成三态（成功 / 失败 / **未知**），或至少不因跳过而中止 |

**同类差异（也值得记）**：

- **`<success>Always</success>` 挡不住 RD2009**：判定用 `matched == 0`（`:430`）而非 `applied`，所以 0 命中的操作即便作者写了 `Always`（引擎里被忽略的失败）我们照样报 warning。rimpatch 默认**只在 `--strict` 下才报** ⇒ 这是与它默认口径的真实差异，也是确定的假阳来源。
- **`Add` 没有 `<value>` 时不算打空**：`:487-488`，1 个匹配 + 无 value ⇒ `matched=1`、不报 RD2009、但**什么都没加**。rimpatch 有专门的 `bad-operation` finding 抓这类「类缺东西」。

### 2.4 缺陷 ④：无日志诊断能力

| 项 | 内容 |
|---|---|
| 现状 | 诊断码 `RD5xxx` 只有 1 个 `AssemblyLoadFailed`，与日志无关；`Player.log` 只在环境探测里被读路径 |
| 性质 | **能力缺口**。环世界的真实错误（`Could not resolve cross-reference` / `Config error in` / `XML error: … doesn't correspond to any field`）**只有真机日志里才有** |
| 价值 | 补上这层，RimDev 就从「离线说会怎样」推进到「真机实际怎样」 |
| 可移植资产 | 见 §1.4 A/B |

### 2.5 顺带发现的其他事实

- **`Diagnostic` 的字段名是 `mod`，不是 `modPackageId`**（JSON 序列化后）。我第一版探针查错键名，得到「归因全空」的假结论 —— **又是探针错误**。
- **`Diagnostic` 已有 `Evidence` 字典**（`Diagnostic.cs:16`），RD3001 的 evidence 里已有 `nearest` / `sameNameOtherDefTypes` / `declarationInScope` / `lookupBasis`。归因基础**是好的**。
- **`ModSuffix` 归一已经做了且做得扎实**：`InheritanceLayer.NormalizeActiveModIds`（`:555`）剥 `_steam`，且有 IL 实证注释（`:540-554`）记录第一版把剥离写在**查询侧**导致的两个错误。**这条不需要借鉴 RimCrow。**
- **`_local` 后缀没归一**（RimCrow 两者都做）。本机 ModsConfig 无 `_local`，**优先低**。

## 三、排查方法论（踩坑清单）

本节全部来自**本轮真实踩过的坑**。共同特征：**无报错、退出码正常、结论却错**。

### 3.1 探针错误（最高频，占本轮误判的一半）

| # | 坑 | 症状 | 判据 |
|---|---|---|---|
| 1 | **路径拼接错**：`ROOT + "\\steamapps\\workshop"` 而 workshop **不在游戏根下** | 映射建了 0 条，导致「已启用 = 0」 | 脚本开头**先断言所有输入路径都存在**，不存在就 `exit 1` |
| 2 | **查错字段名**：`x.modPackageId` 而实际是 `x.mod` | 得到「归因全空」，误判成产品缺陷 | 先 `Object.keys(d[0])` 打印真实字段 |
| 3 | **grep 结果被 cap**：`Select-Object -Last 8` 截掉第二条警告 | 「已修完」被当事实 | 对 grep 做 cap 后的结论**一律不算数**，重跑不带 cap |
| 4 | **`$c` 当字符串 splatting**：`& $exe @c` 传的是字面量 `c` | 七条命令全报「未知命令: c」 | **所有被测对象给出同一异常 ⇒ 先怀疑探针** |
| 5 | **`/usr/bin/time` 不存在**（MSYS bash） | exit 127，看起来像被测程序失败 | 用被测程序自己打印的 `elapsedMs` |
| 6 | **`basename` 遇空格路径报错** | `basename "(x86)/..." extra operand` | 用 `node -e` 或加引号 |
| 7 | **内联 `node -e` 的 `\\` 被 shell 吃掉** | `SyntaxError: Unterminated string` | 复杂脚本**写成文件**再跑 |
| 8 | **`[IO.File]::ReadAllText` 用进程 CWD**，不认 PowerShell `cd` | 读到错误路径 | 一律用绝对路径或 `Join-Path $PSScriptRoot` |

### 3.2 二进制搜索：ASCII vs UTF-16（本轮差点判反）

**`Numbers.dll` 里搜 `Numbers_RimWorld_StatDef_`**：

| 编码 | 结果 |
|---|---|
| ASCII | **-1**（找不到） |
| UTF-16LE | **79157**（找到，紧邻 `StatDef`@79191） |

**.NET 元数据的用户字符串是 UTF-16LE**。只搜 ASCII 会得出「这个前缀是代码拼的 → 不存在」的**相反结论**。

⇒ **判据：搜 .NET 程序集字符串，ASCII 和 UTF-16 都要试**，任一命中即可。这也推翻过一条旧结论（「ASCII 列全 0 ⇒ 引擎不支持 PNG」）。

### 3.3 用真实语料验证假设，而不是"看起来像"

**本轮实例**：我最初把 3,971 条分成 (a) 真不兼容 / (b) 运行期生成 / (c) 待归因，抽样看的样本是 `Twilight`（`ImpactSoundTypeDef "Stab"`）和 `Numbers`（`PawnColumnDef`）。

结果：**这两个 mod 都不在启用集里**（`PMoon.TwilightEGO` / `Mehni.Numbers`，ModsConfig 命中 0 次）。
⇒ 我基于它们的推断，描述的是**不影响当前游戏的 mod**。整个 (a)(b)(c) 分类的前提就错了。

**正确顺序**：先按「引用方是否启用」分桶，再在**启用桶内**细分性质。

### 3.4 门禁的汇总行必须是被算出来的

见 `Docs/08` §8 第 13 条（Task 9c 落地）。一句话：**写死的「0 警告」在有缺陷时仍然会打印**。
必须用一次故意的失败证明它会红。

### 3.5 「行号当身份」类缺陷

XML 里**同一物理行可以有多个 def**（紧凑排版）。凡是用 `(文件, 行号)` 当键的地方都会串味。
本项目已修两处（`ParentChainCheck` / `FieldNameCheck`），**第三次出现时要立刻联想到这个模式**。

### 6.1 日志诊断的码号：用 RD7xxx，不用任务书说的 RD6xxx

**冲突**：任务书说「新增 RD6xxx 段（RD5xxx 已被程序集占用）」，但实测文档里两段都已有归属。

| 段 | 文档出处 | 归属 | 已定义码 |
|---|---|---|---|
| **RD6xxx** | `Docs/01-设计文档.md:931-938`、`Docs/02:467` | **贴图与素材** | RD6001–RD6004、RD6010 |
| **RD7xxx** | `Docs/01-设计文档.md:940-946`、`Docs/02:465-471` | **日志** | RD7001–RD7005、RD7010–RD7013 |

**预检结果**：`DiagnosticCodes.cs` 里 RD6/RD7 **都无常量**，`engine/**/*.cs` **零发射点** ⇒ 两端都是「码表有、代码空」。

**裁决：走 RD7xxx；新增码从 RD7020 起**（RD7014–RD7030 已 grep 确认在文档与代码中全部未出现）。

理由：
1. **文档是权威、代码是投影**（项目一贯纪律）。日志诊断在文档里本来就有专门段，另起 RD6xxx 等于同时违反码表、并占用贴图段。

3. 任务书那句「RD5xxx 已被程序集占用」只说对了一半：真正空着且语义正确的段是 RD7xxx。

**附带**：`Docs/01` §5.5 已定义日志归因的**置信分层** `attributed-by-path` / `attributed-by-defname` / `attributed-by-modname` / `unattributed`，且规定 `unattributed` **不参与 baseline 新增判定**。实现必须沿用这套分层，不要另造。

### 6.2 默认日志路径必须二级回退

**实测**：`GameEnvProbe.cs:232` 拼的是 `<localLow>\Player.log`，但本机 1.7 的真实日志在 **`<localLow>\Logs\Player.log`**（多一层 `Logs` 子目录）。

## 七、可复用探针与工具

本轮踩坑中发现：**有价值的探针写在 `_tmp/` 里等于没写** —— `_tmp/` 整个是 gitignored，
一次清理就没了。所以凡是「以后还会用到」的探针，必须落进 `tools/`（已入库）。

### 7.1 `tools/mdtype` — 只读元数据查继承链（已固化）

**解决什么问题**：判定 `AlienRace.ThingDef_AlienRace` 到底是哪个 Def 的子类。

**为什么不能用常规方法**：
| 方法 | 问题 |
|---|---|
| `Assembly.LoadFrom` | mod DLL 多是 net472，RimDev 跑 net10，**会崩**（`Docs/08` 记过 `ReflectionTypeLoadException`） |
| `ManagedAssemblyCatalog` | 只加载**官方** Managed 目录，看不到 mod 的 `Assemblies/*.dll` |
| 纯字节搜索 | 能找到类型名字符串，但**拿不到继承链** |

**解法**：`System.Reflection.Metadata.PEReader` 读元数据表，不加载、不执行任何代码。

**用法与判读规则见 `tools/mdtype/README.md`**。核心判读：

| 链尾 | 含义 | 处置 |
|---|---|---|
| `→ Verse.Def (外部)` | 直接派生自 `Def` | **不要**归并到具体子类 |
| `→ Verse.ThingDef (外部)` | 是 ThingDef 子类 | 归并到 `ThingDef` |
| `未找到` | 该 DLL 只**引用**不**定义** | 去找提供者 DLL |

### 7.2 二进制字符串搜索：ASCII + UTF-16 双搜

**本轮差点判反的地方**：搜 `Numbers.dll` 里的 `Numbers_RimWorld_StatDef_`。

| 编码 | 结果 |
|---|---|
| ASCII | **-1** |
| UTF-16LE | **79157**（紧邻 `StatDef`@79191） |

**.NET 元数据的用户字符串是 UTF-16LE**。只搜 ASCII 会得出**完全相反**的结论。

**标准模式**（node，避免 shell 转义）：
```js
const b = fs.readFileSync(dllPath);
const ascii = b.indexOf(Buffer.from(needle, "ascii"));
const utf16 = b.indexOf(Buffer.from(needle, "utf16le"));
// 任一命中即为存在
```

**判据**：判「.NET 程序集里有没有某个字符串」，**两种编码都要试**，不能只试一种。

### 7.3 JSON 诊断分析的标准姿势

分析 `check --json` 的大输出（全库 80k 条）时：

1. **先打印字段名**：`Object.keys(d[0])` —— 本轮用错键名（`modPackageId` vs `mod`）得到过「归因全空」的假结论
2. **脚本开头断言输入路径存在**，不存在就 `exit 1` —— 本轮路径拼错（workshop 不在游戏根下）导致映射建了 0 条
3. **闭合校验**：分类结果之和必须等于总数，不等就 `ABORT`
4. **复杂脚本写成文件**，不要内联 `node -e`（反引号、`\\`、空格路径都会出事）

### 7.4 探针代码的固化纪律

| 情形 | 放哪 |
|---|---|
| 一次性分析、跑完就丢 | `_tmp/`（gitignored，随便放） |

### 8.9 日志诊断（RD7xxx）的实现落点

若下一轮做日志诊断，这些是已经查清的**契约**（来自 T3 的只读侦察，2026-11-10）。

**可用的现成接口**：

| 需求 | 现成的东西 |
|---|---|
| 诊断模型 | `Diagnostic` 已有 `Scope.NeedsGame` —— 日志诊断正好用这个 scope，语义精确 |
| 开关白名单 | `CommandFlagSet` 声明 + 在 `CommandFlags.Sets` 登记 + `CommandLine.Usage` 加一行 |
| 环境路径 | `EnvironmentResolution.TryGetEnv` 是**环境唯一来源**，不要另拼路径 |
| 活跃集 | `ModCatalog.ReadActiveMods` 可直接供「提取到的 packageId 是否真启用」交叉比对 |

**七步清单**：

1. 裁决码段 —— 已裁决：**RD7xxx，新增从 RD7020 起**（见 §6.1）
2. `Logs/LogDiagnosisRules.cs` —— 规则的**唯一声明点**：11 条 known_rules + 9 条特征 + 9 个噪音 id + 3 条提取正则（清单见 §1.4）；`Regex` 必须加 `IgnoreCase`
3. `Logs/LogAnalyzer.cs` —— block 模型带行号 + 四层归因（`attributed-by-path` / `-defname` / `-modname` / `unattributed`）+ 活跃集三分支 + 版本号假阳性过滤 + 命名空间噪音
4. `Logs/PlayerLogReader.cs` —— 读 `Player.log` 要用 `FileShare.ReadWrite | Delete` 流式，**游戏运行时文件被占用**，独占读会失败
5. `Cli/Commands/LogCommand.cs` —— 默认路径走 §6.2 的二级回退
6. `SelfTest/Cases/Phase3Task13Cases.cs` —— 每条规则一条用例 + 三条判别性（噪音过滤 / 版本号假阳性 / 活跃集交叉）
7. 门禁 —— `build-all.ps1` exit 0、warning 0、自测全绿且 SKIP 不增加

**归因分层的语义（`Docs/01` §5.5 已定义，必须沿用）**：

| 层 | 判据 | 可信度 |
|---|---|---|
| `attributed-by-path` | 日志里带了文件路径，能定位到 mod 目录 | 最高 |
| `attributed-by-defname` | 只有 defName，靠索引反查所属 mod | 高 |
| `attributed-by-modname` | 只有 mod 显示名（`[author.mod]` 形态） | 中 |
| `unattributed` | 什么都没提取到 | 最低，**不参与 baseline 新增判定** |

**这条纪律很重要**：`unattributed` **不能**参与「比基线新增了几条」的判定 ——
否则每次游戏版本变化导致的通用报错都会算成「新增缺陷」，让门禁变成噪音源。

**日志格式（实测，决定解析器怎么写）**：
```
2026-11-09 22:38:24.965 ERROR [Vulkan] <消息>
    at <栈帧>
```
- 按**行首时间戳**切块，**不要按空行**（消息体内部可能有空行）
- 续行是 4 空格 + `at `
