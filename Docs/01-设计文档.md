## 0. 摘要

RimDev 是一个**离线优先**的环世界 Mod 开发辅助工具。它的核心主张是：

> 现在的 Mod 开发循环里，唯一的裁判是「启动游戏 → 等 2 分钟 → 读 Player.log」。而其中 90% 的错误（字段名写错、def 引用悬空、父类不存在、贴图缺图、程序集依赖坏）**根本不需要 Unity 运行时就能判定**。

RimDev 把这些判定搬到离线，做成秒级命令；把真正需要 Unity 的那 10%（MonoBehaviour 时序、Harmony 补丁执行、渲染、寻路）留给自动化的真机回归，并且用 baseline 差分保证在装有 3967 个工坊 mod 的环境里也**只报新增错误**。

## 1. 目标与非目标

### 1.1 目标（本工具要解决的具体问题）

| # | 痛点（来自历史实证） | RimDev 的对策 |
|---|---|---|
| G1 | 「静态校验永远查不出字段名/def 名不存在，必须开游戏读 Player.log」 | 把 `Assembly-CSharp.dll` 的字段表反射出来，离线校验每个 XML 元素名；把 Core+DLC+已启用 mod+工坊全集的 defName 建成索引，离线校验每条引用 |
| G2 | 同一份 XML 要等 2 分钟才知道对不对 | 离线体检 + 离线 Def 模拟加载，秒级给结论 |
| G3 | 装了 3967 个工坊 mod，日志里几万行错误分不清哪些是自己的 | 日志按 mod / 文件 / def 归因；真机回归用 baseline 差分只报新增 |
| G4 | Dictionary 的 XML 形状、`Inherit="False"` 语义、`Name=` 抽象基类这类坑靠踩 | 把已知坑固化成回归测试用例（§11.1） |
| G5 | 想验证 mod 的 C# 逻辑（如按体型算容量的 `BaysFor`）只能开游戏 | 离线执行引擎：加载 Managed 依赖 + mod DLL，在测试脚本里直接构造 Def 对象、调静态方法 |

### 1.2 非目标（第一版明确不做）

- **不做 Unity 运行时模拟**。不实现帧循环、渲染、寻路、PhysX、随机数种子。
- **不做 Mod 自动生成 / 自动修复**。工具只诊断并给出 `hint`，改动由人或上层 AI 决定。
- **不做 Mod 排序推荐**（那是 BetterModSort 这类 mod 的活）。
- **不做贴图生成**（已有 ComfyUI / 贴图流水线）。
- **不替代 rimsearcher**。rimsearcher 查的是「上一次开游戏时的运行时 Def 真值」，RimDev 查的是「磁盘上这份 XML 加载后会不会崩」。两者互补，RimDev 不重复实现 FTS 搜索。
- **不做 GUI 桌面程序**。人机界面是 DSH 插件的侧栏面板。

### 1.3 诚实边界（会同时写进 `check` 报告的页脚）

| 边界 | 说明 | 工具如何标注 |
|---|---|---|
| 无 Unity 运行时 | 任何触及 `UnityEngine` 原生实现的调用（`Object.Instantiate`、`Time.deltaTime`、`Random`、渲染、`Physics`、`PathFinder`）在离线执行引擎里会抛异常 | 归类为 `RD5006 UNITY_NATIVE_REQUIRED`，**不计为失败** |
| Harmony 时序不可复刻 | 补丁的真实执行顺序、`Prefix` 返回值拦截、多补丁叠加效应无法离线验证 | 只做**目标存在性**校验（`RD5003/RD5004`），时序问题标注 `needs-game` |
| ConfigErrors 只覆盖子集 | RimWorld 的 `ConfigErrors` 有数百条规则，部分是纯数据可判的，部分依赖运行时对象图 | 每条规则带 `scope: offline \| needs-game`，报告里分开统计 |
| 不加载 mod 的 C# Def 工厂 | `thingClass` 等在运行时才实例化 | 只做类型存在性与继承关系校验 |
| 日志是滚动窗口 | `Player.log` 会被下一次启动覆盖，长局里首部启动信息可能被截掉 | 真机回归在启动前先归档日志 |

**为什么放在 `Mods\` 下**：DSH 的文件沙箱以工作区为界（`workspace-write` 只允许写工作区），放在工作区内可避免每次写盘都要 `danger-full-access` 提权。放在游戏 `Mods\` 下的风险是「被游戏当成 mod 扫描」——已确认 RimWorld 只加载含 `About\About.xml` 的子目录，`_rimdev` 不含该文件，因此安全；`rimdev env` 会把「游戏是否误认它为 mod」作为一项自检。

### 3.3 技术选型与理由

| 选择 | 理由 |
|---|---|
| `.NET 8`（LTS） | 本机运行时 `Microsoft.NETCore.App 8.0.0/8.0.11/8.0.21/8.0.30` 与 `10.0.3/10.0.11` 均已安装；8 是最保守的 LTS。SDK 为 10.0.400，可编译 net8.0 |
| C# + `System.Reflection.MetadataLoadContext`（NuGet） | 只读程序集元数据、**不执行代码**，因此能安全检查 net472 的 `Assembly-CSharp.dll` 的字段/类型，不受运行时版本差异影响 |
| `AssemblyLoadContext` + 解析器 | 执行引擎需要真加载；解析器把 `Assembly-CSharp` / `UnityEngine.*` 映射到 Managed 目录（历史已在 pwsh/.NET 上验证可行） |
| `Microsoft.Data.Sqlite` | 索引缓存；本机已有 `Microsoft.Data.Sqlite.dll`（来自 `RimSearcherDataMod`），且 rimsearcher 的 `defs.db` 也是 SQLite，便于交叉验证 |
| `System.Text.Json` | 报告序列化 |
| xunit | 单测框架 |
| DSH 插件用 TypeScript + tsdown | 与生态一致（`dev_scaffold_plugin` 生成） |
| 不引第三方 XML 库 | 需要**保留行号/列号**与原始空白，且要容忍 RimWorld 的宽松 XML；用 `XmlReader` + 自定义承载器实现 |

### 3.4 四个引擎的职责与能力边界

| 引擎 | 输入 | 输出 | 需要游戏运行？ | 需要执行 mod 代码？ |
|---|---|---|---|---|
| **Def 引擎** | mod 目录集 + `ModsConfig.xml` + 目标版本 | 合并后的有效 Def 集合、引用边、加载期诊断 | ❌ | ❌ |
| **元数据引擎** | `Managed\*.dll` + mod 的 `Assemblies\*.dll`（只读元数据） | 类型/字段/枚举/特性清单；字段名与类型校验结论 | ❌ | ❌ |
| **执行引擎** | 同上 + 用户测试脚本 | 测试通过/失败 + 异常分类 | ❌ | ✅（仅纯托管路径） |
| **真机回归引擎** | 目标 mod + baseline | 新增错误集合 | ✅ | ✅（真实全部） |
| **日志引擎** | `Player.log` | 归因后的诊断集合 | ❌（读已有日志） | ❌ |

3. Steam 注册表 `HKCU\Software\Valve\Steam\SteamPath` → `steamapps\common\RimWorld`
4. 常见默认路径
→ 全失败报 `RD1001`。

### 4.2 Mod 模型

```csharp
public sealed record ModInfo
{
    public string PackageId;         // About.xml <packageId>，缺失时为 "local.<文件夹名>"
    public string DisplayName;       // <name>
    public string RootPath;          // mod 目录绝对路径
    public ModSource Source;         // Official | Local | Workshop
    public string? PublishedFileId;  // 工坊目录名（也是 publishedFileId）
    public string[] SupportedVersions;
    public string[] LoadFoldersForTarget; // 解析 loadFolders.xml 后、针对 TargetVersion 的目录列表（已过滤存在的）
    public string[] Dependencies;    // <modDependencies><li><packageId>
    public string[] LoadAfter;       // <loadAfter><li><packageId>
    public string[] LoadBefore;
    public string[] ForceLoadBefore;
    public bool IsActive;            // 在 ModsConfig activeMods 里
    public bool HasAssemblies;
    public string? AboutXmlPath;
    public string? LoadFoldersPath;
    public string? ParseError;       // About.xml 解析失败时记录（→ RD2001/RD1001）
}

public enum ModSource { Official, Local, Workshop }
```

**packageId 去重规则**：同一 `packageId` 出现在多个目录时，**靠前的（官方 > 本地 Mods > 工坊，同级按目录名序）获胜**，后者整份被遮蔽，报 `RD1005`（severity=warning，附被遮蔽路径）。

### 4.3 加载顺序模型

```csharp
public sealed record LoadOrderEntry(
    int Index,
    ModInfo Mod,
    LoadOrderOrigin Origin);   // OfficialData | ActiveMods | DependencyInjected

public sealed record LoadOrder(
    IReadOnlyList<LoadOrderEntry> Entries,
    IReadOnlyList<Diagnostic> Diagnostics);
```

规则：
1. `Data\Core` 永远第 0。
2. `Data\<DLC>` 按 `ModsConfig.xml` 的 `knownExpansions` 顺序；`forceLoadBefore` 参与拓扑排序。
3. `activeMods` 按声明顺序。
4. **不自动注入依赖**：`<modDependencies>` 缺项时报 `RD2010`（warning），但不篡改顺序（避免与游戏的容错行为不一致）。`Origin` 字段保留是为了将来支持 `--auto-order` 时不再改模型。
5. `loadAfter`/`loadBefore` 用作**一致性校验**：若声明与 `activeMods` 顺序矛盾，报 `RD2011`（info）。

### 4.4 Def 原始节点（**保留行号**）

```csharp
public sealed class RawDef
{
    public string DefType;           // 元素名，如 "ThingDef"
    public string? DefName;          // <defName>
    public string? NameAttr;         // Name="..." （抽象基类用）
    public string? ParentName;       // ParentName="..."
    public bool IsAbstract;          // Abstract="True" 或含 Name= 且无 defName
    public bool InheritFalsePresent; // 存在 Inherit="False" 的子元素
    public string? MayRequire;       // MayRequire="packageId"
    public string? MayRequireAnyOf;  // 空格分隔
    public ModInfo SourceMod;
    public string FilePathAbs;
    public string FilePathRelToMod;
    public int Line;                 // 1-based
    public int Column;

}
```

`DefXmlNode`：

### 4.5 有效 Def（模拟加载的产物）

```csharp

{
```

### 4.6 引用边

```csharp
public sealed record ReferenceEdge(
    EffectiveDef From,
    string FromElementPath,   // 如 "comps/li[2]/props/fuelFilter"
    string FieldHint,         // 期望的 C# 字段/属性名（用于给出更准的提示）
    ReferenceKind Kind,       // DefNameString | DefNameList | CSharpType | SoundPath | TexturePath

    string TargetValue,       // XML 里写的值
    int Line, int Column,
    ResolutionStatus Status); // Resolved | Unresolved | TypeMismatch | SkippedByMayRequire

public enum ReferenceKind { DefNameString, DefNameList, CSharpType, SoundPath, TexturePath }
public enum ResolutionStatus { Resolved, Unresolved, TypeMismatch, SkippedByMayRequire }
```

**引用是怎么被识别出来的**（三层，按可靠性从高到低）：
1. **元数据驱动（首选）**：目标 `DefType` 的 C# 类型（由 `DefType` 名 → `Verse.<DefType>` / `RimWorld.<DefType>` 解析，或从 `DefType` 的 `<Class>` 属性）上的字段类型是 `Def` 派生 / `List<Def>` / `HashSet<Def>` → 该 XML 元素就是引用边，期望类型取字段的泛型参数。
2. **约定字段名（兜底）**：字段名匹配已知约定（`def`/`thingDef`/`kindDef`/`hediffDef`/`recipeDef`/`researchPrerequisite`/`*Def`/`*Defs`）但元数据缺失时。
3. **全局引用扫描（只报高置信）**：`<li>` 文本值恰好与某个已知 defName 同形且元素名以 `Def` 结尾。

第 1 层能覆盖绝大多数；第 3 层默认关闭（`--aggressive-refs` 打开）。

## 5. 引擎设计

### 5.1 Def 引擎

#### 5.1.1 扫描（`rimdev index`）

对每个 mod 目录：

1. 读 `About\About.xml` → `ModInfo`（大小写不敏感匹配文件名）。
2. 读 `loadFolders.xml`（大小写不敏感；两种拼写都见过）：
   - 结构为 `<loadFolders><v1.6><li>/</li><li>1.6</li></v1.6>…</loadFolders>`。
   - 取与 `TargetVersion` 匹配的键（`v` + 版本号，支持 `v1.6` 与 `1.6` 两种键名）。
   - `li` 值为 `/` → mod 根；否则为子目录名。**只保留实际存在的目录**，不存在的报 `RD2012`（info，因为很多 mod 写多了无所谓）。
   - 没有 `loadFolders.xml` → 回落策略：若存在 `1.6` 子目录则用它 + mod 根；否则整个 mod 根。
3. 递归枚举 `<loadFolder>\Defs\**\*.xml` 与 `<loadFolder>\Patches\**\*.xml`，记录 `(路径, size, mtimeUtc)` 指纹。

**文件指纹与增量**：SQLite 表 `files(path PK, size, mtime_utc, sha1?, defs_count)`。`size + mtimeUtc` 未变即跳过解析（不读 sha1，省 I/O）。`--verify-hash` 时改为 sha1 比对。

#### 5.1.2 XML 解析（必须保留位置信息）

- 用 `XmlReader`（`IgnoreComments=false`）流式读，自建 `DefXmlNode`。
- 位置：`IXmlLineInfo`（`XmlReader` 实现该接口）→ `LineNumber` / `LinePosition`。
- **注释体含 `--`**：`XmlReader` 会直接抛 `XmlException`。为把这条规则单独报出（`RD2002`），解析前先做一次**廉价预扫**：逐行找 `<!--` 与 `-->`，检查区间内是否含 `--`。预扫只对「首次解析失败」的文件跑，避免全量开销。
- 顶层：只认 `<Defs>` 作为根（RimWorld 支持多根吗？不支持——一个文件一个 `<Defs>`）。`<Defs>` 下的每个直接子元素是一个 def。出现其他根元素 → `RD2013`（warning，且跳过该文件）。

#### 5.1.3 Patch 应用（`PatchOperation*`）

必须实现，因为生态大量使用（本机工坊 528 个 mod 带程序集，绝大多数带 Patches）。第一版实现下列操作类：

| Class | 语义 | 第一版 |
|---|---|---|
| `PatchOperationAdd` | 按 XPath 添加节点 | ✅ |
| `PatchOperationInsert` | 插入（`Order` 属性：Prepend/Append） | ✅ |
| `PatchOperationReplace` | 替换 | ✅ |
| `PatchOperationRemove` | 删除 | ✅ |
| `PatchOperationAttributeAdd/Set/Remove` | 属性操作 | ✅ |
| `PatchOperationSequence` | 顺序执行 `operations`，`onFail` 支持 | ✅ |
| `PatchOperationConditional` | 条件分支（`xpath`/`match`/`nomatch`） | ✅ |
| `PatchOperationTest` | 断言 | ✅ |
| `PatchOperationFindMod` | 按 mod 存在与否分支 | ✅ |
| `PatchOperationAddModExtension` | 添加 modExtension | ✅ |
| `PatchOperationSetName` | 改名 | ⚠️ v2 |
| 自定义 `Class=`（mod 自带补丁类） | 需要执行 mod 代码 | ❌ 报 `RD2014`（info：跳过，需真机验证） |

XPath 支持：RimWorld 的补丁用的是完整 XPath 1.0，.NET 的 `XmlDocument`/`XPathNavigator` 支持它，也支持 `defName`/`ParentName` 等**属性**与元素。第一版在「合并后的 Def 树」上跑 XPath：把 `EffectiveDef` 树包成一个 `XmlDocument` 视图执行 XPath，再用结果定位回 `DefXmlNode`。**要求**：XPath 结果为 0 匹配时，RimWorld 通常静默不管（视操作类型），但我们的工具报 `RD2009`（warning），因为这是最常见的"补丁打空了"症状。

#### 5.1.4 继承解析

- 索引 `Name="X"`（抽象基类）与 `<defName>Y</defName>` 两个命名空间。
- 子 def 的 `ParentName` 先在「抽象命名空间」找，再在 `defName` 命名空间找，都找不到 → `RD2005`。
- 合并：从根父类往下，逐层覆盖同名元素；列表元素（`<li>` 容器）默认**追加**父类已有序号之外的内容（RimWorld 实际是"同名元素整体替换，除非标记 `Inherit="False"`"——详见下方语义表）。
- **继承环**：用访问集合检测，报 `RD2006` 并打断。

**RimWorld 的继承语义（工具必须按这个实现，已按历史实证校准）**：

| 情形 | 行为 |
|---|---|
| 子写同名标量元素 | 覆盖父值 |
| 子写同名列表容器（如 `<comps>`） | **整块替换**父类同名块（历史坑 #2：`<comps Inherit="False">` 改父类 comps 会引发 NRE） |
| 子写同名元素且该元素带 `Inherit="False"` | 不继承父类该元素（等价于清空后只留子值） |
| 子完全没写某元素 | 继承父值 |
| `Name=` 抽象基类 | 不进入 DefDatabase，只能被 `ParentName` 引用 |
| 子 def 写 `<race>` 块 | **整块替换**父类 race（历史坑 #9）：丢 `intelligence`/`thinkTreeMain` 会连环报错 |

> 工具对「子 def 写了 `<race>` 但没有 `intelligence`/`thinkTreeMain`」给出**专项规则** `RD2015`（error），因为在历史项目里这条造成了最长的排查链。

#### 5.1.5 MayRequire

- `MayRequire="packageId"` / `MayRequireAnyOf="a b"`（空格分隔）出现在 def 或任意子元素上。
- 判定集合 = 已安装的 packageId 全集（不是 activeMods！RimWorld 的语义是"已安装"）。
  - 本机 3,967 个工坊 mod 的 packageId 全集就是这个集合。
  - 提供开关 `--may-require-active-only` 用 activeMods 判定（更严格，用于排查"我启用列表里没它"）。
- 不满足 → 该节点整体跳过，并在 `RawDef.SkippedByMayRequire` 记录，报 `RD2016`（info）。

#### 5.1.6 引用解析

对每个 `EffectiveDef` 遍历 `EffectiveRoot`，对每个元素：
1. 用 §4.6 的三层策略判断是否引用边。
2. 解析期望类型（优先元数据给的泛型参数）。
3. 查 `DefIndex`：
   - 命中且类型匹配 → `Resolved`
   - 命中但类型不符 → `RD3003` TypeMismatch（error）
   - 未命中 → `RD3001`（error），并在 `Evidence` 里给出**最相近的 5 个候选**（Levenshtein 相似度 + 同类型 def 名列表）
4. 引用指向的 def 来自 **未启用** 的 mod → 这在真机上会成功（如果 mod 装着）还是失败？**已装即成功**。因此规则是：在"已安装 packageId 全集"的 def 索引里找；找不到才是真悬空。提供 `--only-active` 切换到"只认启用 mod"的严格模式，用于排查"我这套启用列表会不会崩"。

#### 5.1.7 离线 Def 模拟加载（`rimdev sim`）

产物 = `EffectiveDef` 全集 + 加载期诊断。输出形态：

```
rimdev sim --mod ThreatFleet
  → reports/latest.json（完整）
  → 控制台摘要：
      Loaded 41,203 defs from 3,967 mods (target: ThreatFleet)
      Target defs: 233 (ThingDef 96, HediffDef 31, ...)
      Errors: 0   Warnings: 4
      W: RD2009 PatchOperationAdd 未命中 (2) 见 1.6/Patches/...
      W: RD2012 loadFolders 声明了不存在的目录 (2)
```

新增查询子命令（v2）：`rimdev sim --def TF_ThreatHive --show-effective` 打印某 def 的最终树 + 每个值的来源链。

### 5.2 元数据引擎

用 `MetadataLoadContext` + `PathAssemblyResolver`：
- 解析器搜索路径：`Managed\` 全部 dll + 目标 mod 的 `Assemblies\`（以及已启用 mod 的 Assemblies，用于 Harmony 目标跨 mod 校验）。
- 先构建 `Managed` 的 `DefType → C# Type` 映射：
  - `Verse.ThingDef`、`RimWorld.TerrainDef` …（不假设命名空间：**按类型名全程序集搜索**，这是历史踩坑点）
  - `<ThingDef Class="X">` 用类名直接解析。
- 字段集合：`Type.GetFields(Public|Instance|NonPublic)` + `GetProperties`，加上特性别名：
  - `[XmlAlias]` 的 `newName`
  - `[LoadAliases]` 的别名列表
  - `[Unsaved]` 标记的字段不参与校验
  - 忽略 `[IgnoreField]`（如存在）

**字段名校验的输出**：元素名不在集合里 → `RD4001`（error），`Hint` = 最相近的 3 个真实名字（大小写不敏感 + Levenshtein）。**这正是历史痛点的直接解法**。

**枚举值校验**：字段类型为 enum 且 XML 值是字面量 → 校验是否在枚举名集合内（`RD4003`）。注意 RimWorld 的 Def 引用型字段也可能写成 defName 字符串，所以要区分「字段类型是 enum」vs「字段类型是 Def/Def 派生」。

**类型存在性**：`thingClass`、无前缀 `Class=`、`<li Class="...">`（comp 的属性类）→ 在元数据里查类型名（不假设命名空间）→ 不存在报 `RD4004`。历史实证：`CompProperties_Refuelable`/`Building_TurretGun` 在 `RimWorld.*`，而 `HediffComp(Properties)` 在 `Verse.*`。

### 5.3 执行引擎（离线跑 mod 代码）

**进程隔离**：`rimdev test` 主进程 → spawn `RimDev.Worker.exe`（子进程）→ 子进程内 `AssemblyLoadContext` 加载 → 跑用户脚本 → stdout 输出 JSON。理由：mod 代码可能 `Environment.Exit`、死循环、栈溢出；只有进程隔离能兜住。

**加载顺序**（已实证的必需序列）：
1. `mscorlib` / `System.Core` / `netstandard`（由 Metadata/ALC 解析器映射到 Managed 目录）
2. `UnityEngine.CoreModule.dll`
3. `UnityEngine.TextRenderingModule.dll`（画 UI 用 `TextAnchor`）
4. `UnityEngine.IMGUIModule.dll` / `UnityEngine.PhysicsModule.dll` / `UnityEngine.ImageConversionModule.dll`
5. `Assembly-CSharp-firstpass.dll`
6. `Assembly-CSharp.dll`
7. `0Harmony.dll`（**必须是无空格的那个文件名**）
8. 目标 mod 的 `Assemblies\*.dll`
9. 已启用 mod 的 `Assemblies\*.dll`（可选，`--with-active-mods`）

**测试脚本形态（v1 提供两种，避免自造语言）**：

| 形态 | 说明 | 优先级 |
|---|---|---|
| A. 项目内 C# 测试程序集 | `Tests/RimDevTests.csproj` 编译成 dll，引用 `RimDev.Abstractions.dll`；反射发现 `[RimDevTest]` 标记的方法并执行 | v2 |
| B. C# 脚本表达式 | `rimdev test --eval "TF.MechHangarOps.BaysFor(TF_MechWeightClass.Heavy, false)"`，用 Roslyn 编译单表达式 | v1 |
| C. JSON 指令集 | `{"type":"TF_MechModuleDef","name":"TF_Mod_A","fields":{"slot":"Core"}}` + `{"call":"..."}` | v2 |

v1 先做 B（Roslyn `CSharpScript` 或最小 `CSharpCompilation`），因为能在一条命令里验证历史记忆里那个具体需求（"把设计文档里手抄的表变成实测的表"）。

**异常分类**（决定"算不算失败"）：

| 异常 | 分类 | 计为失败？ |
|---|---|---|
| `MissingMethodException` / `DllNotFoundException` / `TypeInitializationException` 其 `InnerException` 指向 `UnityEngine` 原生 | `UNITY_NATIVE_REQUIRED` (`RD5006`) | ❌ 不算失败，报 info |
| `NullReferenceException` / 断言 / 业务异常 | `TEST_FAILED` | ✅ |
| 子进程崩溃 / 超时 | `WORKER_CRASHED` (`RD5007`) | ✅ |
| `FileNotFoundException` 指向缺失的 mod 依赖程序集 | `ASSEMBLY_MISSING` (`RD5002`) | ✅ |

### 5.4 真机回归引擎

流程（`rimdev game run --yes`）：

1. **前置检查**：游戏是否已在运行（`Process.GetProcessesByName("RimWorldWin64")`）→ 在运行则拒绝（`RD8005`）。
2. **备份**：`ModsConfig.xml` → `reports\modsconfig-backup-<ts>.xml`；`Player.log` → `logs\archive\Player-<ts>.log`。
3. **改启用列表**：写入"最小必要集"（Harmony + 目标 mod + 其 `<modDependencies>` + 依赖闭包 + Core/DLC）。用 XML DOM 写，**不手写字符串**（历史坑）。
4. **启动**：写一个 `.lnk`（`TargetPath` = `<GameRoot>\RimWorldWin64.exe`，`WorkingDirectory` = `<GameRoot>`），用 `Start-Process explorer.exe <lnk>` 打开 → **脱离 DSH 的 pwsh 进程树**（否则命令结束游戏就被杀，表现为"干净退出、无 WER 事件"）。也支持直接 `Start-Process -WorkingDirectory`（在用户手动跑的场景）。
   - 可选参数：`-quicktest`（跳过主菜单）、`--dev-mode`（写 `Prefs.xml` 的 `devMode`）。
5. **等待加载完成**：轮询 `Player.log`，命中下列任一「加载完成」标记即视为完成：
   - `Initializing new game with mods:`（本机实测存在，位于 def 加载之后）
   - `[HugsLib] Quickstarter generating map with scenario:`（本机实测存在）
   - 兜底：日志大小连续 N 秒无增长 + 已出现 `RimWorld <version>` 横幅
   - 超时（默认 300 s）→ `RD8002`
   - > **待实测确认（§13-Q2）**：以上标记在不同启动路径（主菜单 / 直接载档 / quicktest）下是否都出现。实施第一步先用现有 `Player.log` 验证标记表，再改脚本。
6. **抓错误指纹**：调用日志引擎，得到 `Diagnostic[]` → 计算 `Fingerprint` 集合。
7. **baseline 差分**：读 `reports\baseline\<name>.json`：
   - 不存在 → 本次即成为 baseline，报 `RD8003`（info）
   - 存在 → 输出「新增」（`RD8004`，error）与「已消失」（info）
8. **收尾**：关闭游戏（`CloseMainWindow` + 等待 + 必要时 `Kill`）→ 恢复 `ModsConfig.xml` → 恢复结果写入报告。
   - **无论成功失败都恢复**（`try/finally`）。

**风险与缓解**：

| 风险 | 缓解 |
|---|---|
| 改 ModsConfig 弄坏玩家配置 | 强制备份 + finally 恢复 + 报告里附备份路径 |
| 游戏卡在启动 | 超时 `Kill` |
| 启动游戏影响用户正在做的事 | 默认拒绝；必须 `--yes`；DSH 插件里需要用户在面板点确认 |
| Steam 云同步 | 本项只改 `%LocalLow%` 下的 Config，不碰云同步文件 |

### 5.5 日志归因引擎

输入 `Player.log`。已知的真实错误形态（本机实测样本）：

| 日志行形态 | 归因手段 | 错误码 |
|---|---|---|
| `Failed to find Verse.TerrainDef named AncientHeavyBridge. There are 383 defs of this type loaded.` | 从 `Verse.<T>Def named <name>` 抽类型与名字 → 反查哪个 mod 的哪份 XML 引用了它（在 Def 索引的引用边表里搜） | `RD7002` |
| `XML error: <publishedFileId>...</publishedFileId> doesn't correspond to any field in type ModMetaDataInternal. Context: <ModMetaData><name>光环 Aura</name>...` | 抽 `doesn't correspond to any field in type <T>` + `Context: <ModMetaData><name>X</name>` → 定位到 `About\About.xml` 的提供者 | `RD7004` |
| `Config error: ...` | 按 mod 名/defName 归因 | `RD7003` |
| `Could not resolve cross-reference: ...` | 抽引用形式 → 用引用边表反查 | `RD7001` |
| `<mod 名>` 出现在堆栈 | 抽程序集名 → 映射到 mod | — |
| 未匹配任何形态的 `Exception` / `Error` | 保留原文，标记 `unattributed` | `RD7005` |

**归因的可靠性分层**（报告里必须标注，避免误诊）：
- `attributed-by-path`：日志里直接出现了 `Mods\<name>\...` 路径 → 高置信
- `attributed-by-defname`：日志里的 defName 在 Def 索引里能唯一定位到某 mod → 中置信
- `attributed-by-modname`：日志里出现 mod 显示名 → 中置信
- `unattributed`：只出现关键词 → 低置信，**不参与 baseline 差分的"新增错误"判定**

> 历史教训直接固化：**抓错误必须全量抓 `Could not resolve|Failed to find`，不能只搜自己 mod 的名字**——`SoundDef` 类错误行不含 mod 名也不点名文件路径。日志引擎默认全量扫，归因留空也不漏报。

## 6. CLI 接口定义

通用约定：
- 所有命令支持 `--json`（默认开；`--no-json` 输出人类可读）、`--out <dir>`（默认 `reports\`）、`--verbose`、`--quiet`。
- 所有命令把报告写 `reports\latest.json` + `reports\latest.md`（除 `env`/`asm probe` 这类纯查询）。
- 路径参数可以是绝对路径、工作区相对路径、或 mod 目录名（在 `Mods\` 与工坊里按名字/packageId 模糊解析）。

### 6.1 `rimdev env`

```
rimdev env [--json]
```
探测并打印 `GameEnv` + 健康度自检（Managed 是否可读、索引是否已建、`_rimdev` 是否被误认成 mod、rimsearcher 是否可用）。
退出码：0 正常；4 环境不满足。

### 6.2 `rimdev index`

```
rimdev index [--scope all|active|target] [--rebuild] [--verify-hash] [--workshop] [--no-workshop]
```
| 参数 | 默认 | 说明 |
|---|---|---|
| `--scope` | `all` | `all` = 本地 Mods + Data + 工坊；`active` = 只索引启用列表；`target` = 只索引目标 mod |
| `--rebuild` | false | 丢弃缓存全量重建 |
| `--verify-hash` | false | 用 sha1 而非 size+mtime 判定变更 |
| `--no-workshop` | — | 跳过 3,967 个工坊 mod（调试用，秒级） |

输出：`summary.indexStats`。首次全量预计数分钟；二次增量秒级（只处理变更文件）。
退出码：0；1/4 见通用表。

### 6.3 `rimdev check`

```
rimdev check [<mod>] [--all] [--rules <RD 码,逗号分隔>] [--ignore <RD 码>] [--severity <error|warning|info>]
             [--only-active] [--aggressive-refs] [--max-items <n>]
```
| 参数 | 默认 | 说明 |
|---|---|---|
| `<mod>` | 自动探测：工作区里含 `Source\*.csproj` 的目录，若唯一则用它 | 目标 mod（目录名 / packageId / 路径） |
| `--all` | false | 对所有已启用 mod 体检 |
| `--rules`/`--ignore` | 空 | 规则筛选 |
| `--severity` | `info` | 最低输出级别 |
| `--only-active` | false | 引用解析只认启用 mod（严格模式） |
| `--aggressive-refs` | false | 打开第 3 层引用识别（更多命中，也可能更多假阳性） |

检查规则（§7 的 RD2xxx / RD3xxx / RD4xxx / RD5xxx / RD6xxx）。
退出码：0 无 error；2 有 error。

### 6.4 `rimdev sim`

```
rimdev sim [<mod>] [--def <defName>] [--show-effective] [--dump <path>] [--only-active]
```
离线 Def 模拟加载。`--def` + `--show-effective` 打印某个 def 的最终 XML 树与每个值的来源链。`--dump` 把 `EffectiveDef` 全集写成 JSONL（便于上层 AI 分析）。
退出码：同 `check`。

### 6.5 `rimdev asm`

```
rimdev asm probe <TypeName> [--field <name>] [--json]
rimdev asm list  [--filter <substr>] [--assembly <name>]
rimdev asm refs  [<modOrDll>]
rimdev asm harmony [<mod>]
```
| 子命令 | 用途 |
|---|---|
| `probe` | 回答"这个类型/字段到底存不存在"。**这是历史痛点 G1 的直接工具**。`--field` 时额外打印字段类型、是否 `[XmlAlias]`、别名列表 |
| `list` | 枚举 Managed 里的类型（按名子串过滤） |
| `refs` | 依赖检查：`GetReferencedAssemblies()`（**不用 `ReflectionOnlyLoadFrom`**，.NET Core 不支持）；报告外来自 mod 的依赖 |
| `harmony` | 扫 mod DLL 的 `[HarmonyPatch(typeof(X))]`，校验 X 与目标方法存在；同时报告补丁打在原版还是别的 mod 上 |

### 6.6 `rimdev log`

```
rimdev log [--file <path>] [--tail <n>] [--since <ts>] [--mod <pkgId>] [--baseline <name>] [--archive]
```
默认读 `Player.log`。`--archive` 先把当前日志复制进 `logs\archive\` 再解析（防被下次启动覆盖）。
输出：按 `Code` / `ModPackageId` 分组的诊断 + 「全量关键词命中数」对比「成功归因数」（**故意把未归因数摆在明面上**，防止误判"零错误"）。
退出码：0；2 有 error 级归因结果。

### 6.7 `rimdev game`

```
rimdev game run [<mod>] --yes [--baseline <name>] [--timeout <sec>] [--keep-open] [--dev-mode] [--quicktest]
rimdev game baseline list|rm|show <name>
```
`--yes` 缺失 → 退出码 6，并打印将要执行的动作清单（干跑）。`--keep-open` 用于人工接管（不自动关游戏）。

### 6.8 `rimdev test`

```
rimdev test [<mod>] --eval "<C# 表达式>" [--ref <dll>] [--with-active-mods] [--timeout <sec>]
rimdev test [<mod>] --file <测试文件.cs>
```
在子进程里加载 Managed + mod DLL 后执行表达式，打印返回值 JSON 与异常分类。
退出码：0 通过；2 测试失败；1 工具错。

### 6.9 `rimdev report`

```
rimdev report [--format md|json|text] [--last <n>]
```
汇总最近若干次运行到一个 Markdown（供人读）+ 给 AI 的"问题清单"纯文本块（便于直接粘贴/注入到会话）。

## 9. 缓存与性能

### 9.1 SQLite schema

```sql
-- 索引元数据版本，用于 --rebuild 判定
CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT);
-- 例如 ('schema_version','1'), ('game_version','1.6.4871 rev591'), ('last_full_index','...')

CREATE TABLE mods (
  package_id   TEXT PRIMARY KEY,
  display_name TEXT,
  root_path    TEXT NOT NULL,
  source       INTEGER NOT NULL,       -- 0 Official / 1 Local / 2 Workshop
  published_id TEXT,
  supported    TEXT,                   -- 空格分隔
  load_folders TEXT,                   -- 针对目标版本解析后的目录，分号分隔
  deps         TEXT,
  load_after   TEXT,
  load_before  TEXT,
  is_active    INTEGER NOT NULL DEFAULT 0,
  about_path   TEXT,
  parse_error  TEXT,
  scan_ts      INTEGER
);
CREATE INDEX idx_mods_root ON mods(root_path);

CREATE TABLE files (
  path       TEXT PRIMARY KEY,
  mod_id     TEXT NOT NULL,
  kind       INTEGER NOT NULL,        -- 0 Defs / 1 Patches / 2 About / 3 Assemblies / 4 Texture
  size       INTEGER NOT NULL,
  mtime_utc  INTEGER NOT NULL,
  sha1       TEXT,
  def_count  INTEGER,
  parse_ok   INTEGER,
  scan_ts    INTEGER
);
CREATE INDEX idx_files_mod ON files(mod_id);

-- 轻量 def 索引（不保留 XML 原文）
CREATE TABLE defs (
  def_name   TEXT NOT NULL,
  def_type   TEXT NOT NULL,
  parent     TEXT,
  name_attr  TEXT,
  is_abstract INTEGER NOT NULL DEFAULT 0,
  mod_id     TEXT NOT NULL,
  file_path  TEXT NOT NULL,
  line       INTEGER,
  may_require TEXT,
  PRIMARY KEY (def_name, def_type, mod_id, file_path, line)
);
CREATE INDEX idx_defs_name ON defs(def_name);
CREATE INDEX idx_defs_type ON defs(def_type);

-- Textures 清单（反向对账用）
CREATE TABLE textures (
  path      TEXT PRIMARY KEY,
  mod_id    TEXT NOT NULL,
  size      INTEGER NOT NULL,
  mtime_utc INTEGER NOT NULL,
  width     INTEGER,
  height    INTEGER
);
```

### 9.2 性能目标与策略

| 场景 | 目标 | 策略 |
|---|---|---|
| 首次全量索引（3,967 mod） | ≤ 8 分钟 | 只用 `XmlReader` 流式抽 def 头（读到 `</li>`-level 即止不做完整树），只对目标版本目录；SQLite 事务批量提交（每 5000 行）；并行度 = 逻辑核数 |
| 增量索引（无变更） | ≤ 3 秒 | 文件指纹比对；不打开未变文件 |
| 增量索引（改 1 个 mod） | ≤ 2 秒 | 只解析变更文件 |
| `check`（目标 mod，索引已建） | ≤ 5 秒 | 只建目标 mod 的完整 XML 树 + 元数据引擎懒加载 |
| `sim`（全量合并，含 patch） | ≤ 30 秒 | patch 与继承只在内存里做，不落盘 |
| `log`（195 KB 日志） | ≤ 1 秒 | 单遍正则 + 索引查表 |

超时保护：索引阶段按 `--timeout`（默认 900 s）中断并保存已完成部分（下次接着增量）。

### 9.3 磁盘占用估算

- `defs` 表：工坊全集估计 30–60 万条 × 约 150 B ≈ 50–90 MB
- `textures` 表：估计 5–15 万条 ≈ 10 MB
- `files` 表：估计 20–40 万条 ≈ 30 MB
- 合计 **≤ 150 MB**，可接受；`rimdev index --rebuild` 可随时重建。

## 10. 安全设计

| 动作 | 风险 | 策略 |
|---|---|---|
| 写 `ModsConfig.xml` | 弄坏玩家启用列表 | 仅 `game run` 使用；先备份；`finally` 恢复；失败报 `RD8006` 并给备份路径 |
| 启动游戏 | 占用用户机器、可能卡住 | `--yes` 必需；插件里二次确认；超时 `Kill` |
| 执行 mod 代码 | 崩溃 / 死循环 / 副作用 | 仅 `test` 命令；**子进程隔离**；超时 `Kill`；默认不执行任何 mod 代码（`check`/`sim` 都是纯静态） |
| 读工坊 3,967 目录 | I/O 压力 | 只读；索引增量；`--no-workshop` 可跳过 |
| 写工作区之外 | 沙箱拒绝 | **不写工作区之外**（唯一例外：`ModsConfig.xml` 与 `Player.log` 在 `%LocalLow%`，属用户明确授权的游戏配置，且已有备份机制） |
| 删除任何文件 | 不可逆 | **工具不删任何用户文件**；清理只针对自己的 `cache\`、`reports\`、`logs\` |

## 11. 测试策略与用例

### 11.1 单元测试用例（把历史踩过的坑固化成回归）

每条用例 = 一个最小 fixture（几行 XML + 一个 stub 元数据类型表），断言产出的 `Diagnostic` 码与关键字段。

| # | 用例 | Fixture | 期望 |
|---|---|---|---|
| T01 | XML 注释含 `--` | `<!-- a --- b -->` | `RD2002`，行号指向注释起始 |
| T02 | `<comps Inherit="False">` 覆盖父类 | 父 def 有 comps，子 def 写 `Inherit="False"` | 不报错，且 `EffectiveDef` 的 comps 只含子类项 |
| T03 | `PawnKindDef` lifeStages 数与 race 不一致 | race 无 `lifeStageAges`，PawnKind 写 1 个 | `RD2015` 之外的专项规则（`RD2018` 待加，见 §13-Q3） |
