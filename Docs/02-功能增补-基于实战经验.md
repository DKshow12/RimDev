## 0. 本文为什么存在

`01` 是我在没有读项目实战记录的情况下写的骨架。读完 `ThreatFleet\Docs\` 的 5 篇经验文档 + 两份真实日志后，发现：

1. **原设计漏掉了最有价值的几类能力**（名字查证、XML 形状顾问、API 查证、四步验证编排、反模式规则包）。
2. **原设计有 3 处与实际不符**（归因来源、baseline 成本、重复诊断），必须修正。
3. **手上多了一份真实回归语料**（修复前日志），它比任何构造的 fixture 都值钱。

本文逐条给出**证据 → 需求 → 功能设计**，不做无证据的猜测；所有数字都出自实际命令输出。

## 2. 对 `01` 的三处修正（有新证据，原设计不对）

### 2.1 修正一：日志归因的来源不是"自研"，而是**三级**，且第一级是别人的 mod

**证据链**（本轮实测）：

1. 归档日志 `20261014-1710-Player-prev.log` 里，每条 XML/交叉引用错误后面都跟着结构化归因块：
   ```
   XML error: <canBeDamagedByExplosions>false</canBeDamagedByExplosions> doesn't correspond to any field in type ThingDef. Context: <ThingDef …>
   [XmlSource] Mod=威胁舰队 · 碎片子机 [Threat Fleet: Fragment Drones] (dsh.threatfleet.fragments) File=C:\…\ThreatFleet\1.6\Defs\ThingDefs_Items\TF_QuestItems.xml Root=ThingDef
   ```
   ```
   Could not resolve cross-reference to Verse.WorkTypeDef named Repair (wanter=mechEnabledWorkTypes)
     -> [交叉引用被使用: Repair]
        - [Mod: 威胁舰队 · 碎片子机 [Threat Fleet: Fragment Drones] (dsh.threatfleet.fragments)] ThingDef[defName=TF_Drone_Construction]/race/mechEnabledWorkTypes
          File: C:\…\ThreatFleet\1.6\Defs\ThingDefs_Races\TF_Drones.xml
        - [Mod: Core (Ludeon.RimWorld)] Defs/RecordDef[defName=TimeRepairing]/measuredTimeJobs
          File: C:\…\Data\Core\Defs\Misc\RecordDefs\Records_Time.xml
   ```
2. **这些字符串不在任何 Managed 程序集里**（对 `RimWorldWin64_Data\Managed\` 全部 108 个 dll 做 ASCII+UTF16 扫描，0 命中）→ 不是游戏原生的。
3. 定位到提供者：**`com.bettermodsort.rimworld`（工坊 3673408015，"Better Mod Sort (And Error Inspector)"）**，其 `1.6\Assemblies\BetterModSort.dll` 含 `XmlSource` 字符串。
4. 其语言文件 `Languages\ChineseSimplified\Keyed\BetterModSort.xml` 给出了完整标签表：
   | 键 | English | ChineseSimplified |
   |---|---|---|
   | `BMS_Error_SourceMod` | `Source MOD` | `来源 MOD` |
   | `BMS_Error_File` | `File` | `文件` |
   | `BMS_Error_CrossRefUsedIn` | `Cross-ref used in` | `交叉引用被使用` |
   | `BMS_Error_InheritanceChain` | `XML Inheritance Chain (ParentName)` | `XML 继承链 (ParentName)` |
   | `BMS_Error_PatchInvolving` | `Patch may be involved` | `Patch 可能涉及` |
   | `BMS_Error_SourceNotFound` | `Source not found in DefSourceMap` | `在 DefSourceMap 中未找到来源` |
   | `BMS_Error_AnalysisHeader/Footer` | `========== Error Analysis ==========` | `========== 错误分析 ==========` |
   另有 `BMS_Log_XmlTrackerCleared` 暴露其内部结构：**`DefSourceMap` / `XmlBuckets` / `PatchSourceMap`**。
5. **标签是本地化的**（有 English/ChineseSimplified/ChineseTraditional/Russian 等）→ **解析器绝不能硬编码中文标签**。

**修正后的设计**：

```
归因引擎三级（逐级降级，报告里必须标注用的是哪一级）

第一级 · 原生 Context 反解（永远可用，不依赖任何 mod）
  RimWorld 自己的 "XML error: … Context: <ThingDef …><defName>X</defName>…"
  → 从 Context 里反解 defName / 元素路径
  实测证据：L287/L289/L291 的 Context 里都能直接取到 <defName>TF_Wreck_OnslaughtMkI</defName>

第二级 · BetterModSort 归因块（若启用；信息最全，含补丁来源与继承链）
  → 标签表从 Languages\<当前语言>\Keyed\BetterModSort.xml 动态读取
  → 再退回内置多语言表（en / zh-Hans / zh-Hant / ru）
  → 按**结构**解析（`-> [label]` 后跟缩进 `- [Mod: …] <DefType>[defName=…]/<path>` 与 `File: …`），
    不按文本匹配，因此换语言也能解析

第三级 · 自研索引归因（我们自己的 Def 索引 + 引用边表）
  → 用于：没有 Context 的错误（如 `Failed to find Verse.TerrainDef named AncientHeavyBridge`）
  → 用于：跨文件反查"是谁引用了这个悬空名字"
```

**新增自检项（副产品）**：BetterModSort 的 `DefSourceMap` 是**运行时真值**（def → 来源文件），我们的 Def 索引是**静态真值**。两者对同一条错误给出不同文件时，说明我们的补丁/继承模拟有偏差 → 报 `RD7011`（warning，"离线模拟与运行时归因不一致"）。这是**用别人的运行时数据校准我们的静态模拟**，成本极低、价值极高。

**风险与降级**：
- 用户可能不启用 BetterModSort → 第一级与第三级仍然工作；`rimdev env` 把"归因增强 mod 未启用"作为 `RD7010`（info）提示，**不作要求**。
- BetterModSort 版本升级可能改标签 → 因为按结构和语言文件解析，兼容性强；另加一条：解析失败时保留原文并按第三级归因（永不丢诊断）。

### 2.2 修正二：baseline 差分**不必跑两次游戏** —— 日志轮转就是免费的基线

**证据**（本轮实测，同一天内两次观测）：

| 时刻 | `Player.log` | `Player-prev.log` |
|---|---|---|
| 本轮开始（早） | 195,932 B / 4,205 行 | 62,718 B |
| 本轮中途（晚） | 44,624 B / **318 行** | 62,718 B / **422 行**（含 17 条 `Could not resolve`、14 条 `List item found with name`、5 条 XML error、2 条 Config error） |

`Player.log` 被下一次启动覆盖，**而游戏自己把上一份留成了 `Player-prev.log`**。也就是说：**每启动一次游戏，就自动得到一份"上一次"的基线，无需工具干预**。

**修正后的设计**：
- `rimdev log --diff` 默认对比 `Player.log` ↔ `Player-prev.log`，输出「新增错误 / 已消失错误」。
- 真正需要"多次运行基线"的场景（v4 的 `game run`）仍保留 `reports\baseline\<name>.json`，但**不再是唯一路径**。
- **日志归档器（F14）成为前置步骤**：`rimdev log --archive` 与 `rimdev game run` 启动前，先把两份日志复制进 `logs\archive\<ts>-*.log`。
  - 本轮就是靠手工归档才保住了那份含 17 条错误的语料（见 §4）。

### 2.3 修正三：诊断必须**按指纹去重** —— 一次启动会出现两次加载

**证据**（同一份日志内重复）：

| 现象 | 位置 |
|---|---|
| `<publishedFileId>` 的 XML error 出现 **2 次**（L64、L407） | `光环 Aura` 的 `About.xml` 被扫两次 |
| `Config error in TF_Wreck_OnslaughtMkI` 出现 **2 次**（L358、L364） | Defs 被加载两遍（模组列表阶段 + 实际开局阶段） |
| 第二次的归因标签是**英文**（`XML Inheritance Chain`）而第一次是中文（`XML 继承链`） | L361 vs L367 —— 语言在两次加载之间不同！ |

**结论与设计**：
1. `Diagnostic` 必须带稳定 `Fingerprint`，**同一指纹只报一条**，附 `occurrences` 与全部出现行号。
2. **健康判据不能用"错误行数"**，要用"去重后的诊断数"——否则会把 2 倍当成回归。
3. 标签语言在同一份日志里可能混用（中文与英文），进一步证明 §2.1 的"按结构解析"是对的。
4. 首轮 `About.xml` 扫描阶段就报错，说明 **RimWorld 会扫描所有已安装 mod 的元数据，而不仅是启用的**（`光环 Aura` 并不在 17 个启用 mod 里）→ 元数据层索引必须覆盖全部 3,967 个 mod（与 `01` §2.4 的结论一致，此处再获独立证据）。

## 3. 新增功能设计（F 系列）

> 约定：`rimdev` 命令统一 `--json`；查询类命令沿用 rimsearcher 的退出码语义（0 成功 / 2 查无此项 / 1 工具错）。

### F1 名字查证器 `rimdev name` ★★★

**解决**：E1（猜名字已造成 8 次加载期错误）。

```
rimdev name check <name> [--kind def|type|field|enum|sound|worktype|stat|body|...] [--type <DefType>]
rimdev name scan  [<mod>] [--aggressive]          扫描目标 mod 全部引用型值，一次报出全部不存在项
rimdev name suggest "<语义描述>" [--kind <...>]    不知道名字时按语义找候选
rimdev name table <字段路径>                       列出某字段在不同 def 上的实际取值集合（借助索引）
```

**判定顺序（权威性排序，与 `14` 纪律 1 的查证手段一致）**：
1. 元数据引擎：名字是否是 `Assembly-CSharp.dll` 里的**类型 / 字段 / 属性 / 枚举成员**
2. Def 索引：名字是否是某个 defName（含 `Name=` 抽象基类）
3. SoundDef / TextureDef 路径类：走索引的对应类型
4. 都不中 → 报不存在 + **最相近候选**（大小写不敏感 + 编辑距离 + 同前缀）

**输出示例（对着历史 8 例验证）**：

| 查询 | 期望输出 |
|---|---|
| `rimdev name check Repair --kind worktype` | ❌ 不存在（1.6 共 23 个 WorkTypeDef）；候选：`Construction`(距离3)、`Research`(距离6)、`Hauling`(距离6) |
| `rimdev name check CarryCapacity --kind stat` | ❌ 不存在；候选：**`CarryingCapacity`**（拼写差异） |
| `rimdev name check MechanoidCentipede --kind body` | ❌ 不存在；候选：**`MechanicalCentipede`** |
| `rimdev name check Shot_MachineGun --kind sound` | ❌ 不存在；候选：`Shot_Minigun`、`Shot_MachinePistol` |
| `rimdev name check Building_Collapse --kind sound` | ❌ 不存在；候选：`Bridge_Collapse`、`Roof_Collapse`、`BuildingDestroyed_Metal_Big` |
| `rimdev name check canBeDeconstructed --kind field --type ThingDef` | ❌ 不存在（全程序集无此字段）；候选：`building/alwaysDeconstructible`、`resourcesFractionWhenDeconstructed` |
| `rimdev name check UltraHeavy --kind def --type MechWeightClassDef` | ✅ 存在 |
| `rimdev name check CompProperties_Refuelable --kind type` | ✅ 存在，`RimWorld.CompProperties_Refuelable`（**不假设命名空间**） |

**`name scan` 的价值**：把"一个错误一个错误地等游戏报"变成"一次性报全部"。这正是 `01` §5.1.6 引用解析的**查询侧接口**，二者共用索引。

`name suggest` 用 def 的 `label`/`description` 与字段注释做模糊匹配，回答"我想要一个『修东西』的工作类型，叫什么"。

### F2 XML 形状顾问 `rimdev shape` ★★★

**解决**：E2 + E3（Dictionary 踩 3 次；游戏自己说判据是"custom XML loader method"）。

```
rimdev shape <DefType>.<字段路径>
rimdev shape <DefType>.<字段路径> --samples <n>     同时给原版真实先例
rimdev shape --field <名字>                          不知道路径时按字段名搜
```

**判定逻辑（关键）**：

```
1. 解析字段的 C# 类型 T
2. 判断 T 是否实现/拥有自定义 XML 加载器：
     LoadDataFromXmlCustom(XmlNode) 的【实例】方法存在？（RimWorld 的约定名）
     ★ 修正（2026-10-14 实测）：**是实例方法，不是静态方法**。全程序集扫描：实例命中 **65** 个类型、静态命中 **0** 个。
       对照：ThingDefCountClass / PawnKindDefCount 都有实例版（签名 `(XmlNode)`）→ 裸元素写法；IntRange 没有 → 走 `<li>` 形式。
     或 T 是 List/Dictionary 且元素类型有该实例方法
3. 分派输出模板：

   T = 标量（string/int/float/bool/enum）            → <字段名>值</字段名>
   T = Def 派生                                       → <字段名>目标DefName</字段名>
   T = List<U>，U 有自定义加载器                      → 裸元素（元素名=U 的 defName 语义）
   T = List<U>，U 无自定义加载器                      → <字段名><li>值</li></字段名>
   T = Dictionary<string,V>                           → <li><key>k</key><value>v</value></li>
   T = Dictionary<Def,V>，每类自定义                  → <字段名><DefName>v</DefName></字段名>
4. 附原版真实先例（在 Data\Core + DLC 的 XML 里找同类型字段的实际切片，给 文件:行 + 原文）
5. Hint 里引用游戏原文措辞：「<X> is not <li>, and which does not have a custom XML loader method」
```

**对着历史 4 例验证**：

| 查询 | 期望 |
|---|---|
| `rimdev shape TF_MechModuleDef.factors` | `Dictionary<string,float>` → `<li><key>fragment_size</key><value>1.0</value></li>`；先例 `Buildings_PsychicRituals.xml` 的 `qualityWeights` |
| `rimdev shape ThingDef.killedLeavings` | `List<ThingDefCountClass>` + **有自定义加载器** → 裸元素 `<Shard>3</Shard>`；先例 `Races_Fleshbeasts.xml` |
| `rimdev shape IncidentDef.fixedMembers` | `Dictionary<PawnKindDef,int>` → 先例 `Factions_Misc.xml` 的 `pawnGroupMakers.options`（每类自定义） |

## 10. 一句话总结

读完成实战经验后，工具的重心从「**静态校验 + 真机回归**」调整为「**名字/形状/API 三张查证表 + 21 条反模式规则 + 三级日志归因 + 四步验证编排**」——
其中**日志归因**这一环原本被低估，而本轮证据显示：游戏自己（与一个可选 mod）已经把最难的归因做好了，工具该做的是**语言无关地解析它、与自己的离线索引交叉校准、并坚持全量而不自欺**。
